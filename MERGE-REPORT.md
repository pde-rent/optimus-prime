# Merge report — `merge/upstream-0.7.3`

Bringing the Bun-only / de-Python fork refactor (`fork/main`, 4 commits on `875aba965`,
last one a large checkpoint) onto upstream `origin/main` (13 commits on the same base).

## Strategy: merge, not rebase

`git checkout -b merge/upstream-0.7.3 origin/main && git merge --no-ff fork/main`

Rationale:

- Our side is effectively **one giant checkpoint commit** (260 files, +15.7k/-34.5k). Rebasing
  would replay that single commit against 13 upstream commits — the same conflict set, but with
  no shared merge base recorded and no way to re-run the resolution incrementally.
- A merge records both parents, so a future `git merge origin/main` has a real base and will not
  re-present the same 60 both-touched files.
- The de-Python refactor *deletes* whole subsystems. In a merge, modify/delete conflicts surface
  once, explicitly, and the deletion can be confirmed on the merits. Under rebase they would be
  replayed as churn.

Merge direction: branch from `origin/main`, so in conflict markers **`HEAD` = upstream** and
**`fork/main` = our refactor**.

## Non-conflict changes made to get the build green

Both are **pre-existing in `fork/main`**, not caused by this merge: the fork switched the toolchain
to Bun but the repo still ships only `package-lock.json`, which `bun install` does not honour.

1. **`bunfig.toml` (new)** — `[install] linker = "hoisted"`. Bun's default isolated linker hides
   transitive `@smithy/*` (a dependency of `@aws-sdk/client-bedrock-runtime`) from `tsgo`, so
   `packages/ai/src/providers/amazon-bedrock.ts` fails to typecheck with three `TS2307`s.
2. **`package.json` overrides** — pinned `"@mistralai/mistralai": "2.2.1"`, the version
   `package-lock.json` pins. Bun resolves `^2.2.0` to `2.6.3`, which imports the optional peer
   `@opentelemetry/api`; that is not installed and esbuild fails the coding-agent bundle.

## Open items for a human

1. **`bun.lock` is untracked.** A Bun-only fork that still commits `package-lock.json` and no
   `bun.lock` has non-reproducible installs; that is what forced the two workarounds above. The
   lead should decide whether to commit `bun.lock` and retire `package-lock.json`. Left untracked
   here rather than guessing.
2. **`a9a86550`'s `result.failed` reporting has no analogue.** Upstream tells the model which
   names could *not* be revived after a restore; `BunReplRestoreResult` only carries
   `restoredNames`. Our prompt says "redefine any you need", so nothing is silently wrong, but a
   failed-names channel in the bun-repl restore protocol would be a faithful port. Not attempted —
   it is a feature, not a merge decision.
3. **Provider trim vs upstream test fixtures.** Our `KnownProvider` no longer includes the
   Cloudflare / Vercel / HuggingFace / Fireworks / opencode / xiaomi providers. Upstream keeps
   adding live-network tests against them (`stream.test.ts` here). Every such collision will
   recur on the next merge; consider either restoring those provider entries or deleting the
   corresponding describe blocks outright so there is nothing to conflict with.
4. **`scripts/render-logo.py` is still tracked.** It survived the de-Python pass on both sides
   (it is a build-time logo utility, not runtime), but if "no Python anywhere" is the rule it
   should go.
